Hour 8: Parsing HTML Like a Surgeon

The problem: Substack wraps article content in nested divs with class names like body markup and available-content. I need to:

  1. Find the actual article container

  2. Walk the HTML tree node by node

  3. Convert each element to Markdown equivalent

  4. Preserve structure (headers, lists, links, images)

  5. Strip Substack-specific junk

New approach:

python

def html_to_markdown(element):
    if element.name == 'h1':
        return f"# {element.get_text()}\n\n"
    elif element.name == 'h2':
        return f"## {element.get_text()}\n\n"
    elif element.name == 'p':
        return f"{element.get_text()}\n\n"
    # ... 30 more cases

This works! Sort of. Until I hit:

  • Nested lists (bullets inside bullets)

  • Links containing images

  • Code blocks with syntax highlighting

  • Block quotes with attribution

  • Inline formatting (bold, italic, strikethrough)

Each edge case requires another conditional. The function grows to 150 lines. I’m building a state machine without admitting I’m building a state machine.

At 11 PM, I refactor the whole thing using a recursive tree walker. Much cleaner.

python

def process_node(node, depth=0):
    markdown = ""
    for child in node.children:
        if isinstance(child, NavigableString):
            markdown += str(child)
        else:
            markdown += process_element(child, depth)
    return markdown

I test it on my “Computational Skepticism” article. The output looks... almost right? Headers are preserved. Links work. Images have alt text.

But the frontmatter is still missing.

## Day 2.5: The Next.js Side

The converter produces MDX files. Now I need a Next.js app to render them.

Dynamic routing structure:
```
app/
  substack/
    [slug]/
      page.tsx    ← Renders individual articles
    page.tsx      ← Renders archive/index

The archive page is straightforward: read metadata.json, display a grid of article cards.

The individual article page is where it gets interesting. I’m using next-mdx-remote to parse MDX at runtime:

typescript

import { compileMDX } from 'next-mdx-remote/rsc'

const { content, frontmatter } = await compileMDX({
  source: mdxSource,
  options: { parseFrontmatter: true }
})
```

First test: Load the MDX file. It compiles! Open the browser.

White screen.

Check the console:
```
Error: Hydration failed because the initial UI does not match what was rendered on the server.
```

Of course. React is trying to hydrate server-rendered HTML, but the MDX components don't match between server and client.

The fix: Use `'use client'` directive for interactive components only. Keep the article rendering on the server.

After restructuring: it works. Articles load. Styling is clean. Links to the original Substack post appear at the bottom.

Next.js 13+ requires me to explicitly tell it which dynamic routes to pre-render at build time. I need to scan the _content/substack/ directory and return all the slugs:

typescript

export async function generateStaticParams() {
  const files = fs.readdirSync('app/_content/substack')
  const slugs = files
    .filter(f => f.endsWith('.mdx'))
    .map(f => ({ slug: f.replace('.mdx', '') }))
  return slugs
}

What I’d Do Differently

Start with the edge cases. I spent hours on the happy path (simple paragraphs and headers), then got wrecked by nested lists and inline code. Should’ve collected the gnarliest Substack posts first and tested against those.

Write tests. I was cowboy-coding: make a change, run the script, inspect output manually. A proper test suite would’ve caught the frontmatter bugs earlier.

Document the Substack export format. I reverse-engineered it through trial and error. Should’ve written down the structure as I discovered it. Would’ve saved time when debugging.

Make the script idempotent. Currently, if it fails halfway through, I have to start over. Should’ve added checkpointing: “Already converted 23/45 posts, resuming from post 24...”

But honestly? The biggest thing I learned wasn’t technical.

Platforms will optimize for platforms, not for you. Substack wants you locked into their ecosystem. They make money when you’re dependent on their discovery, their recommendations, their network effects. Your SEO equity doesn’t benefit them—it benefits you. So they remove it.

The solution isn’t to rage-quit every platform. It’s to use platforms for what they’re good at while also owning the parts that matter: discoverability, portability, long-term equity.
