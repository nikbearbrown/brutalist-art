Picture the modern job hunt. You open LinkedIn. Then Indeed. Then the careers page of every company you admire, bookmarked in a browser tab graveyard stretching back six months. You apply, and then you wait, and then you apply again. The process is not broken in any single dramatic way — it is broken in aggregate, in the thousand small frictions that compound into exhaustion.

Jobsekr is being built as a direct answer to that exhaustion. A team effort still taking shape, it is designed to be a job aggregation platform — one searchable dashboard pulling fresh postings from over 1,600 company career pages, updated within hours of going live. In its current form, it already surfaces over 76,000 active listings. But the ambition does not stop at aggregation. The application tracking layer is being wired to let users save roles, update statuses, and visualize their pipeline.

Beneath all of it, deeper in the architecture, is a feature that interests me most: the intelligence layer. The part that will read your resume, understand who you are, and start connecting you to the world.

That intelligence layer is what I am building.

What the Pipeline Does

You upload a PDF. You click a button and assume something, somewhere, will read it. Here is what actually happens on the other side of that button.

The file lands in secure, per-user cloud storage the moment it is uploaded. A database row is written with a single status: pending. That flag is a request whispered into a queue. Every fifteen minutes, the pipeline wakes up, scans for pending resumes, and gets to work. It extracts text from the PDF, sends that text to a large language model with a carefully engineered prompt, validates the structured response, and writes the parsed skills, experience, and education back to the user’s profile — ready to be matched against job listings. From upload to parsed profile, the whole process is automatic, invisible, and happens while you sleep.

The backend is built on Supabase — handling the database, storage, and authentication in one platform, with row-level security policies ensuring each user's data is strictly isolated. The AI layer is powered by a provider architecture I designed around Groq's API, which runs a fast, lightweight language model well-suited for structured extraction tasks. Groq is the default, but the system is built so that if Groq fails or becomes unavailable, it can fall back to Ollama — a locally hosted model that runs entirely on your own machine, with no external API dependency. Switching between them requires no code changes, only a configuration update. The architecture was designed from the start to treat the model as a replaceable part, not a fixed foundation.

The Problems, and How I Navigated Them

While building the pipeline, some problems surfaced that were not anticipated.

The first was the PDF itself. Not all PDFs are equal. A well-formatted document yields text cleanly. A scanned resume — printed, signed, re-uploaded — yields nothing but pixels. If the first extraction attempt returns too little usable text, the pipeline automatically escalates to optical character recognition, reconstructing the content from the visual image of the page. Every failure mode — corrupt files, password-protected documents, image-heavy layouts — has a defined, graceful path. No resume disappears without an explanation.

The second was the model. Getting a large language model to return clean, structured data consistently is harder than it sounds. The first versions of the prompt produced responses full of preamble, markdown formatting, and fields that did not match the schema. Prompt engineering here was not a one-time task — it was iterative, testing how the model handled edge cases like partial dates, overlapping job titles, and resumes with no education section at all. The solution was precision: define every field explicitly, give concrete examples, and leave the model no room to improvise. The response is then validated against a strict schema before anything is written to the database. If it fails validation, the pipeline retries once with a more forceful instruction. If it fails again, the resume is marked as failed — loudly, never silently.

The third was the question of what not to overwrite. When parsed data is ready to be written, the system must decide what to do with records that already exist. Skills are always refreshed on re-upload — that is expected. But employment history and education are different. If a user has hand-entered and carefully curated their work history, the pipeline has no business replacing it with whatever the model extracted from a PDF. The system checks for existing records first, and if they are there, it leaves them alone. It fills empty profiles; it does not overwrite considered ones. That distinction — between extracted data and curated data — is encoded directly into the logic.

The fourth was rate limits. The pipeline calls an external AI API, and that API has a ceiling on how many requests it will accept per minute. The naive approach — run as fast as possible, crash when throttled — was never an option. Instead, the pipeline enforces a deliberate delay between each call and, if it hits a rate limit anyway, resets the affected resume back to pending and stops the batch cleanly. The next scheduled run picks up exactly where it left off. No resumes are lost. The system degrades on purpose, then recovers automatically.

What Building This Taught Me

There is a particular kind of learning that only happens when you are responsible for something running close to production. Reading about distributed systems is not the same as writing a batch processor that claims jobs atomically so two runners never process the same resume. Reading about prompt engineering is not the same as iterating on instructions until a model reliably returns clean structured data instead of a paragraph that begins with “Certainly! Here is the information you requested.”

Backend architecture with Supabase revealed itself to be less about the database and more about the contracts between layers. Row-level security, storage permissions, service-role versus user-level access — these are not afterthoughts. They are the architecture. The status state machine — pending → processing → completed / failed — is a simple pattern, but designing it correctly required understanding how the database and pipeline interact under concurrent load.

Large-scale AI pipelines are not models. They are systems that contain models. The AI component is one node in a larger graph of extraction, validation, transformation, and persistence — and it is not even the most fragile node. The most fragile node is the PDF that arrives corrupted, or the resume where every bullet point is an image embedded in a table. Robustness in AI pipelines means designing for the input you did not expect, not the input you did.

LLM architecture for production applications is fundamentally about isolation and replaceability. The provider abstraction I built was not over-engineering. It was the minimum viable structure for a component that will almost certainly need to change. Models improve. Costs shift. Rate limits tighten. The architecture that survives is the one that treats the model as a dependency to be injected, not a foundation to be built upon.

Future Work

The pipeline is not complete yet. The automated workflow still needs to be wired to production. The test suite is staged but unfinished. The local model fallback — which would automatically retry a failed cloud API call against a self-hosted model — remains an open item. But the core is running. Every fifteen minutes, a process wakes up and reads the resumes that people uploaded while they slept. It extracts their skills, their history, their education — carefully, without fabrication, only what is explicitly stated — and writes it to a database where it waits to be matched against one of 76,000 open roles.

What is built so far is the foundation. The next layer of intelligence is already mapped out. The pipeline will be extended to generate vector embeddings — mathematical representations of both a resume and a job description — which can then be compared using cosine similarity to produce a genuine match score between a candidate and a role. Alongside that, a "Tailor Resume" feature is in the roadmap: a user clicks it on any job listing, and the system returns AI-rewritten bullet point suggestions, reworking the candidate's existing experience to better fit the specific language and requirements of that role. The parsing pipeline being built now is the prerequisite for both — without structured, queryable profile data, neither feature is possible.
