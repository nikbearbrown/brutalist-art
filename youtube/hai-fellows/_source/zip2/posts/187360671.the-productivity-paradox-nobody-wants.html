The Almost-Right Trap (Or: Why 95% Correct Is Worse Than 0% Correct)

Professor Bear: Here’s a question I ask my students at Northeastern: Would you rather debug code that’s 0% complete or code that’s 95% complete?

The obvious answer is 95%. But think about what that 95% number actually means in practice.

When you write code from scratch, you make explicit decisions at every branch:

  • “Should this search be case-sensitive? Let me think... probably not for user experience.”

  • “What happens at 100,000 records? I need to paginate.”

  • “Multi-field fuzzy matching? That requires a different index strategy.”

Each decision teaches you something about the problem space. You discover edge cases through the act of implementation. This is what the documents call “Intent Debt”—the accumulated cost of unclear, unspecified requirements that you uncover by trying to write them down.

Now consider the AI workflow:

You: “Build a user search feature.”

AI: Instantly generates 200 lines of plausible-looking code

You: “Looks good, ship it.”

Three weeks later in production: Users complain that searches are case-sensitive. Performance degrades at scale. Multi-word names don’t match properly.

Professor Bear asks: Why didn’t you catch these issues during review?

Because the code looked correct. It followed best practices. It had proper error handling. It used popular libraries. Your brain saw syntactic correctness and inferred semantic correctness.

The 5% of wrongness isn’t in the parts that look wrong. It’s in the subtle authorization failures, the race conditions, the unbounded database queries—the things that require understanding the entire system’s architecture.

The Fundamental Asymmetry: Probabilistic Generation vs. Deterministic Requirements

Professor Bear asks: Why can’t AI just “get better” at being correct?

Because of a fundamental asymmetry in how AI and software engineering work:

AI Models:

  • Generate code based on statistical likelihood

  • Pattern match against training data

  • Optimize for plausibility, not correctness

  • No internal model of your specific business logic

Software Engineering Requirements:

  • Must be deterministic (same input → same output)

  • Must handle edge cases (which are rare in training data)

  • Must align with tacit organizational knowledge

  • Must integrate with existing system architecture

No amount of model improvement can close the gap between “statistically likely” and “provably correct.”

Here’s the equation that matters:

P(AI_generates_correct_code) < 1.0

But:
P(production_system_must_be_correct) = 1.0

That gap—between <1.0 and =1.0—is where all the verification work lives. And that gap doesn’t shrink just because AI gets better at pattern matching.

In fact, the better AI gets at generating plausible-looking code, the harder verification becomes, because the errors become more subtle.

From the security data:

  • Syntax errors: AI handles brilliantly (-76%)

  • Privilege escalation paths: AI creates more (+322%)

The AI is excellent at local correctness and terrible at global correctness. And global correctness is what actually matters for production systems.
